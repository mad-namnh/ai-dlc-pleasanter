# Plan — configuration the KB does not cover: one framework procedure

- **Date / branch / parent commit:** 2026-11-11 / `brownfield-adr` / *set when building starts — after task P2-6 (ADR-0020…0022) is committed (Nam, 2026-11-11: wait for P2-6)*
- **Objective:** when a project needs a SiteSettings shape that the KB does not cover, the framework itself says how it becomes known and verified — once, for every project — instead of each project improvising (a person clicking it in the UI, an agent reading the Pleasanter source on its own, a per-project `--accept-unverified` record, a per-project `${env:x}` for a group id).
- **Origin:** project `pls-demo-contracts` P3 (2026-11-11). DES-001 needed a "today … today+90" date range on two views (C-2), a total of 月額 per 取引先 (C-3) and a reminder to a group (C-4). The KB had none of these shapes. The agent read the Pleasanter source (`Libraries/Settings/View.cs`, `SiteSettings.cs`, `Aggregation.cs`, `Reminder.cs`, `Libraries/Mails/Addresses.cs`, branch `main`) and found `NearCompletionTime` + `NearCompletionTimeBeforeDays/AfterDays`, `Aggregation.Types` (Count 0, Total 1, Average 2) and `[Group<id>]` address tokens. `release-plan` then refused `NearCompletionTimeBeforeDays/AfterDays` (ADR-0001 scope). Nam: "the automation must be guided by the framework, not done one project at a time".
- **Tier:** Critical — new ADR, scope evidence behind a release-plan refusal (ADR-0001, I9), principal mapping (permissions-adjacent), KB.
- **Scope:**
  1. **ADR-0023 (Proposed)** *Configuration shapes the KB does not cover*. Order of sources: KB → canonical exports already in git for the same environment → Pleasanter source at the tag of the environment's recorded version (cited by path and tag; an entry from source is marked `source-derived, not verified`) → a KB probe (`references/probes/*.json`, `expect_stored` and record tests) → `pls kb-verify --env <dev>` run by the person → KB entry verified on that version + scope key in `pls_scope.py` with the evidence. A project uses the shape only after the last step; the scope refusal is unchanged (no relaxation). A person setting it in the UI and `harvest` remains the fallback when the source does not answer. Options for Nam: (a) this order; (b) allow a project dev release with `--accept-unverified` citing a source-derived entry; recommendation (a).
  2. **`pls kb-verify` date tokens with an offset** (`$today+90`, `$today-1`), so a probe can test a relative range. Test.
  3. **Principals inside mail addresses:** `[Group<id>]` / `[User<id>]` / `[Dept<id>]` in `Reminders[].To`, `Notifications[].Address` (and Cc/Bcc if present), `Processes[].Notifications[].Address` ↔ `[${principal:x}]` in git (unpack / pack); an unmapped token stays raw and is lint L-PERM-01. Tests (round trip, unmapped, wrong type).
  4. **Probes and KB entries** (through `pls-kb-curator`, from the source evidence and then the kb-verify report): `NearCompletionTime` view + site days (range today−Before … today+After, no status condition); `Aggregations` (`GroupBy`, `Type` 0/1/2, `Target`); `Reminders` fields and `To` tokens; date filter keywords `Today` / `ThisMonth` / `ThisYear` / `\t`; D8 addition: `Columns[Title].ValidateRequired: true` is a default on Issues (seen in the R-20261111-01-dev round trip of `pls-demo-contracts`).
  5. **`pls_scope.py`:** add `NearCompletionTimeBeforeDays`, `NearCompletionTimeAfterDays` only after the probe passed on dev 1.5.2 (evidence in the docstring and the KB). Test.
  6. **Skills:** `pls-p2-solution-designer`, `pls-p3-config-builder`, `pls-x-lifecycle` (P3 step 5 "scope"): replace "a property you cannot find is a probe for P2" / "the person writes a decision record" with the ADR-0023 procedure; versions in `skills/README.md`.
  7. Docs in the same commits: `docs/architecture.md` (I9 text, P2/P3), `docs/adr/README.md`, `HANDOFF.md`.
