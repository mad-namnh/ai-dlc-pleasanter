# ADR-0014: Trust boundaries — what `pls` enforces and what it trusts

- **Status:** Proposed (2026-11-09; revised 2026-11-10 after the design review, roadmap P0-7) — Nam accepts, changes or rejects **each row** (column "Nam's decision"); a row holds only once accepted
- **Date:** 2026-11-09
- **Deciders:** Nam
- **Related:** I3, I4, I7 (`docs/architecture.md` §2), ADR-0003, ADR-0004, ADR-0008, ADR-0010, ADR-0011, ADR-0012, ADR-0013; `docs/reviews/design-review-2026-11-09/` (A6, `99-final-report.md` §4)

## Context

`pls` enforces many rules in code (write guards, gate records, side-effect refusals). Some things it cannot enforce, because they happen outside the tool: who typed a command, whether a person really said the words recorded as their approval, who may edit files on the operator's machine, and what the network allows. The design review standard (A6) requires these boundaries to be written down, with the risk and an owner, so that a reviewer can tell a deliberate boundary from a missing control. Without such a record every gap is a finding "missing trust-boundary ADR".

This ADR lists the boundaries as they are on 2026-11-10. It does **not** accept gaps that code can close; those are listed separately at the end and stay findings until fixed.

**Revision 2026-11-10.** The design review found that TB-1, TB-2, TB-3 and TB-8 named compensating controls that do not hold, and that seven boundaries present in code had no row. The controls below are restated as they are (what exists, and what does not), and rows TB-9…TB-15 are added. Code fixes made since (roadmap P0-1…P0-6) are reflected in "What `pls` does enforce".

## Open questions

- [ ] For a customer staging environment (`cstg`): are gate records protected beyond git (signed commits, protected branch on a remote, or a record store outside the agent's reach)? Project repositories are local-only today. — *Nam, before the first cstg project*
- [ ] For production: the customer-side runner and package (ADR-0003) and its input verification; customer responsibilities — *customer IT (TD-02), roadmap P0-9*
- [ ] TB-15: a dedicated least-privilege Pleasanter user per project for stg instead of an administrator key — *Nam, before cstg*

## Options

### Option A — Enforce everything in code
- Pros: no trust assumptions.
- Cons: impossible for human intent (the tool cannot know what a person said) and for the operator's own machine (the person who can run `pls` can also edit its files).

### Option B — Write each boundary down, with owner, stage and compensating controls; close in code what code can close
- Pros: reviewable; gaps that code can close stay visible as findings.
- Cons: the boundaries hold only as long as their owners and controls do.

## Decision

**Option B (proposed).** Each row below, once Nam accepts it, holds **for the stage named in the row**. A later stage needs the follow-up named in the row first. "Compensating controls" lists only controls that exist today; missing ones are named as missing and do not count.

**Gaps that are not boundaries** (code can close them; they remain review findings until fixed or until Nam records an explicit decision in `docs/tech-debt.md`):
- ~~approval bound to a release id, not to the payload content~~ — closed 2026-11-09: a G4 record stores the digest of each planned release (`pls_release_digest`); `apply` / `bootstrap` on stg refuse a release changed since G4;
- ~~recovery status after a failed restore~~ — closed 2026-11-09: `recovery-required`, decided by read-back;
- behaviour when the run log cannot be written (it fails open; roadmap P2-5);
- ~~handling of a timeout after the server has written~~ — closed 2026-11-09: `uncertain`, no blind restore or retry; `mark-applied` reads back.
- ~~migrations (`bulkupsert`) run only through the browser runner, without a guard~~ — closed 2026-11-10: `pls migrate` over HTTP; the runner's `bulkUpsert` refuses non-dev plans.
- ~~the typed confirmation accepts piped stdin~~ — closed 2026-11-10: typing counts only at a terminal; `pls test` outside dev needs the G4 of the release under test or the person's confirmation (ADR-0008);
- the run log does not record the effective `allow_write` of the connection used (TB-1).

## Consequences

- Easier: the review can classify each gap as an accepted boundary (with this ADR) or a finding; every row names its missing controls, so acceptance never records false assurance.
- Harder / costs: every boundary must be re-checked before a later stage; TB-1, TB-2, TB-3 and TB-12 carry most of the I4 risk and need stronger controls before customer data is involved.
- Follow-up: Nam decides each row; decide the open questions before `cstg`; revisit TB-7 when the e2e runner decision is made (`pls-p4-e2e-tester`).
