AI-DLC for Pleasanter — lifecycle and demo guide

How the framework takes a natural-language request to a released Pleasanter app: who does what in each phase, where a person must approve, and the script for running the equipment-loan demo. Verified end to end on dev on 2026-11-05 (release R-20261105-01-dev).

1. Lifecycle diagram

Phase (agent works, using a skill) Gate (a person approves) pls (deterministic tool) Person acts in Pleasanter / terminal

2. Invariants that hold in every phase

I1Git is the desired state; Pleasanter is the runtime.
I2A deploy sends the complete configuration, after a drift check.
I3AI has no path to production and holds no production keys.
I4People approve at G1–G4; AI never approves its own work.
I5Standard settings before code; a server script needs a written reason.
I6pls decides (diff, classify, coverage); AI explains.
I7No secrets and no business data in git.
I8Every requirement traces to config and tests, and back.
I9Every escaped defect becomes a rule, check, KB entry or skill change.

3. Phases — what goes in, what runs, what comes out

P1 · Requirements

Request → testable requirements

Skill
pls-p1-requirements-analyst
Input
The request, saved verbatim in requirements/sources/
Does
EARS requirements (one shall each), acceptance criteria, derived requirements from impact, questions for the customer in Japanese with [assumed] defaults
Output
REQ-*.md, requirements/index.md
Stops at G1
P2 · Design

Simplest Pleasanter mechanism per requirement

Skill
pls-p2-solution-designer + KB pls-kb-pleasanter
Does
Sites and type (Results / Issues), columns and slots, statuses, views, processes, summaries; ladder rung per element; permission design (roles → groups → matrix); impact analysis; classification
Output
DES-*.md, design/roles.json, slot-ledger.json, traceability.json, environments.json
Stops at G2
P3 · Build

Config in git, deployed to dev

Skill
pls-p3-config-builder
pls
principals → bootstrap-plan / bootstrap → export / unpack → edit config/ → canon, lint, coverage → release-plan → apply
Done when
Round trip shows 0 differences; otherwise fold the live value back and apply again
No gate
P4 · Verify

Acceptance criteria proven on dev

Skill
pls-p4-test-writer
Does
API test specs (tests/api/*.json), negative paths, config checks for screen-only rules; role tests per profile (deferred in the demo); triage every failure to P1/P2/P3/KB
pls
test, coverage, lint
Output
releases/<release>/g3-verification.md
Stops at G3
P5 · Release

Make the tested state official

Skill
pls-p5-release-manager
dev
Record only: export → drift = 0 since the tests
stg
release-plan → person runs apply → smoke tests
prod
Package only; the customer applies it
Output
diff-report.md (Japanese summary), approvals.md
Stops at G4
P6 · Operate

Keep git and Pleasanter in step

pls
drift, classify
Does
Records the baseline in ops/drift/; later drift is explained, classified, and accepted (→ change request to P1) or reverted
No gate

4. Gates — what the approver sees

GateEvidence presentedDecision recorded in
G1 requirementsREQ table (ID, title, type, derived?); open questions with [assumed] defaults; out-of-scope items. In stage demo: approve with the assumed defaultsStatus line of each REQ; requirements/index.md
G2 designDesign table (element → setting → REQ, rung); rejected alternatives; classification; permission matrix and the groups to create; open pointsStatus line of DES-*.md
G3 verificationRound trip 0, lint 0, coverage, test results, role tests or their deferral, manual screen checksg3-verification.md
G4 releaseDrift 0 (dev) or accepted plan (stg); Japanese diff report: user-visible changes, data and permission impact, order, rollback, open itemsapprovals.md; REQs marked released; drift baseline

"Looks good, continue" counts as approval. Silence does not. The agent writes the decision only after the person states it, with name and date. pls apply and pls bootstrap need the person: they run the command, or they allow --yes for a named target.

6. Demo script

Say the line to Claude Code (any language), then show the listed file or screen. Plan about an hour with discussion at each gate.

  1. Start — P1 requirements stops at G1

    You sayBuild the app for this customer request. You may use --yes for dev in this session. + paste the mail from spec.md
    Agent doesFinds where the project stands; saves the mail; writes REQ-001…008 with acceptance criteria and 12 questions (Japanese) with [assumed] defaults
    Showrequirements/index.md — the REQ table and the questions; point out the assumptions

  2. Approve G1 — P2 design stops at G2

    You sayG1 approved with all assumptions, continue
    Agent doesTwo sites (equipment Results, loans Issues), 返却 process, conditional count summary, overdue view, permission matrix and design/roles.json; rungs 1–2 only
    Showdesign/decisions/DES-001-….md — design table, permission matrix, rejected alternatives, open points

  3. Approve G2, create groups — P3 build no gate

    You doCreate the groups named in design/roles.json in Pleasanter, with exactly those names (no members needed)
    You sayG2 approved, groups created, continue
    Agent doesprincipals binds the groups → bootstrap creates the two sites → export / unpack → builds config/ → canon / lint → release-plan → apply --yes → round trip 0
    ShowRefresh the Pleasanter folder: 備品台帳 and 貸出管理 appear and are configured. git log --oneline: one commit per step

  4. P4 verify stops at G3

    Agent doesWrites and runs T-001…T-010 on dev; checks 社員 restrictions in config (role tests deferred); coverage; writes g3-verification.md and asks for manual screen checks
    You doScreen check: as 社員 the register is read-only and 貸出管理 is hidden; as 総務 返却 shows only on 貸出中 loans. Open a loan, press 返却 — the register count drops back to 0
    ShowTest summary and coverage; the 返却 button live

  5. Approve G3 — P5 release stops at G4

    You sayG3 approved, screen checks done, continue
    Agent doesExport → drift 0 since the tests → diff-report.md (Japanese customer summary) → approvals.md
    Showreleases/<release>/diff-report.md, top part

  6. Approve G4 — done P6 baseline

    You sayG4 approved, continue
    Agent doesRecords G4, marks REQs released, writes ops/drift/<date>-dev-baseline.md, commits
    Showrequirements/index.md (released), the baseline file, git log --oneline

  7. Optional epilogue — P6 drift no gate

    You doChange something in the Pleasanter UI, e.g. add a choice to 種別
    You sayCheck dev for drift.
    Agent doesFinds the change, classifies it, asks: accept as a change request (→ P1) or revert

7. If something goes off script

SituationWhat to do
The agent asks a question at a gateAnswer it. "Approve with changes: …" is fine.
pls principals reports a group MISSINGThe group name in Pleasanter must match design/roles.json exactly. Create it with that name, or tell the agent which existing group to use (it updates roles.json and the DES). Seen in the verified round: existing zz_demo_* groups were used instead.
A test fails in P4Let the agent triage: build → P3, design → P2/G2, requirement → P1/G1, KB wrong → framework. A test may only be changed with a written reason. Seen: T-007 compared a $var in siteConfig, which the runner does not substitute (TD-14h).
Coverage shows a GAP for a role-only requirementWith role tests deferred, permission-only requirements (e.g. REQ-008) cannot have an API test. The approver decides at G3: accept on configuration + drift 0 + manual screen check.
pls refuses a plan (drift, slots, migration)The agent explains and asks. Do not tell it to bypass the refusal.
Connection errorspython pls.py http-check --env dev, then the troubleshooting table in docs/setup.md.

8. Reset for the next run

Pleasanter

Delete the demo folder's contents (the two sites), or create a new folder and use its id as parent_id. Test records start with 「テスト」 if you only want to clear data.

Local

Delete the project folder and run pls init again. The demo project stays local; only the framework repo is pushed.
