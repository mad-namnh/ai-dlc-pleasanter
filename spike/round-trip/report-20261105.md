## Endpoint confirmation (step 0)

| Operation | 1.5.2 endpoint | Response | Notes |
|---|---|---|---|
| Get site | `POST /api/items/{id}/getsite` | `{StatusCode, Response:{Data:{…site}}}` | Works with the browser session, no ApiKey needed |
| Create site | `POST /api/items/{parentId}/createsite` | `{Id, Message, StatusCode}` | Top-level folder: `parentId = 0`, `ReferenceType: "Sites"` |
| Update site | `POST /api/items/{id}/updatesite` | `{Message, StatusCode}` | **Full replacement** (see D4) |
| Copy site package | `POST /api/items/{id}/copysitepackage` | `Response.Data` = JSON string `[{OldSiteId, NewSiteId, ReferenceType, Title}]` | Includes an old→new ID map |

Additional volatile fields for normalization: `LockedTime`, `LockedUser`, `ApiVersion` (added to `config.example.json`).

## `updatesite` semantics (D4)

| Experiment on a copy | Result |
|---|---|
| Send `Views` with one element missing | The element is deleted |
| Send `Reminders: []` | All リマインダー are deleted |
| Send `Columns` without the `ClassH` definition | The column definition is deleted (column falls back to defaults; cell data not deleted — not yet verified on a site with data) |
| Omit the `Notifications` and `Aggregations` keys entirely | All deleted |
| Write the original back | Restored with 0 differences |

→ `updatesite` = **full replacement of SiteSettings** (desired state), not a merge.

## Cross-site references (D3, D6)

Locations holding another site's SiteId in the two sample sites:

| Location | API create | Site package |
|---|---|---|
| `Columns[].ChoicesText` (`[[SiteId]]`) | Keeps original ID ❌ | Remapped to new ID ✅ |
| `Links[].SiteId` | Keeps original ID ❌ | Remapped to new ID ✅ |
| `Summaries[].SiteId` (cross-site 集計) | Keeps original ID ❌ | Remapped to new ID ✅ |
| String inside `ServerScripts[].Body` | Keeps original ID ❌ | **Keeps original ID ❌** |

Real risk: a copy created via the API still has `Summaries` pointing to the original site → entering records into the copy writes aggregates into the **original site's data**.

## Site package vs API

- Preserved by site packages but not by the API: **automatic remapping** of structured references to new IDs.
- Preserved by the API but not by site packages: inherited permissions kept as-is (a site package with `IncludeSitePermission:false` added one permission); exact field-level control.
- Neither: SiteIds inside scripts.

## Decision

**Conditional Go.**

- Round-tripping via the API (getsite/createsite/updatesite) is **reliable**: 0 differences, idempotent, clear desired-state semantics.
- Condition before closing the spike: **round 2** with additional sample sites covering the remaining 7 core components.
- Design impact (ADR-0001/0003/0004/0005 and review-findings D3–D6 updated):
  1. Deploys always send the **complete SiteSettings**; partial payloads are forbidden.
  2. **Pre-deploy drift check is mandatory** (`updatesite` silently overwrites customer edits).
  3. ID resolution must handle **4 kinds of locations**, including strings in scripts; convention: scripts must not hard-code SiteIds.
  4. **Blocking plain-text secrets** in configuration is a mandatory framework check.
