# Behaviours that change designs

Each entry: what happens, why it matters, what to do. IDs refer to `docs/review-findings.md` in the framework repository.

| ID | Behaviour (version) | Consequence | Do this |
|---|---|---|---|
| D3 | SiteIds hard-coded in script strings are not remapped by site packages or the API (1.5.2) | A copied site's script silently reads another environment's data (seen in slice #1: stg read dev) | Use `${site:<name>}` in git; `pls pack` resolves per environment; lint L-REF-01 |
| D4 | `updatesite` replaces SiteSettings entirely (1.5.2) | Partial payloads delete settings; deploys overwrite customer UI edits | Complete payloads only (L-DEP-01); drift check before every deploy |
| D5 | Secrets in scripts are visible through `getsite` | Anyone with site-settings read access gets the key | No secret values in configuration; gateway pattern; L-SEC-01 |
| D7 | Shared server script with top-level `const`/`let` → every save fails `ServerScriptExecutionFailed` when combined with another script (1.5.2) | Whole site unusable for record saves | `var` in shared scripts; L-SCR-01 |
| D8 | Save-time normalisation: defaults added, default values dropped (1.5.2) | False drift if git is not canonical | `pls canon`; after first deploy, export → unpack; L-CAN-01 |
| D9 | Checkbox view filter is 2-state (only "checked") (1.5.2) | Cannot express "not yet done" with a checkbox in a display condition | Model states with **Status** or a choice column |
| D10 | API process execution enforces the display condition (1.5.2) | Display condition is a real guard, not just UI | Rely on it; test it with a negative API test |
| D11 | Removing a choice that records already use is data-impacting | Reverting a customer's added choice can orphan data | Resolve drift via `pls classify`; prefer accept + requirement |
| — | Adding a new status | Every view, notification condition and script that enumerates statuses must be checked (e.g. an "open items" view filtering on the old status list hides records in the new status) | Include a status-impact step in every design that adds a status |
| — | Server script time limit ~10 s | Slow external calls abort the save | Timeouts below 10 s; gateway with its own timeout |
| D12 | Removing a column / choice / status definition keeps stored values (1.5.2): column value hidden but kept, comes back when the slot is defined again; removed choice/status stays on the record and appears as an orphan option on the edit screen | "Removed" ≠ "deleted"; reusing a slot shows someone else's old data | Treat removals as data-impacting; never reuse a slot that held data; migrate values before removing a choice/status |
| D13 | `bulkupsert` with `Keys` = update matched records, create the rest (1.5.2) | One call per migration batch | Use for migrations; key on a business identifier column |
| D14 | API record updates did not create versions (`Ver` stayed 1) (1.5.2) | No undo from history after a data change | Back up affected records first (runner `backupRecords`) |
| D15 | `updatesite` accepts `InheritPermission` + `Permissions` (`Type,Id,Value`); keys omitted → permissions untouched (1.5.2) | Permissions can be deployed, but principal IDs differ per environment | `config/<site>/permissions.json` with `${principal:x}`; lint L-PERM-01 |
| D16 | Summary (集計, configured on the **child** site, e.g. `{Type: Total, SourceColumn: NumA, LinkColumn: ClassA, SiteId: parent, DestinationColumn: NumB}`): every child create/update/delete recomputes the **full** total for that parent (empty = 0). Adding/changing a Summary via `updatesite` does **not** recalculate existing parents; there is no API sync endpoint (`synchronizesummaries` → 400). Updating one child record (even with an unchanged value) recalculates its parent (1.5.2) | Past data shows 0 until a child changes | Classify Summary changes as data-impacting; migration = touch one child per parent after the release |
| D17 | `EditorReadOnly` is a screen setting only: the API can still write the column (1.5.2) | A "read-only" total can be overwritten by API clients or bulk imports | Do not rely on it for integrity; recompute (D16) after imports |
| D18 | `bulkupsert` updates only the columns given (others kept); if a key value matches **several** records the call returns HTTP 400 「条件に一致するレコードが複数存在します。」 with 0 added / 0 updated (1.5.2, PR-3) | A non-unique key stops the migration | Check key uniqueness in the backup before running; key on a unique business id |
| D19 | Site permission value **1 (Read)** for a group (1.5.2, PR-1/PR-2 with a test user): records can be read on the site and on child sites that inherit its permissions; attachments can be downloaded; `getsite` is readable; create / update / delete / process execution / comments → **HTTP 403** 「この操作を行うための権限がありません。」. The edit screen hides save/delete, **but still shows process buttons whose display condition matches** (e.g. エスカレーション) — pressing them is refused (403) (corrected after slice #2 T-015; the first probe had no matching process). A site without rights → 404 | Read-only role = value 1; note `getsite` exposes site settings (D5) | Use 1 for view-only roles; add Export (32) only if the role must export |
