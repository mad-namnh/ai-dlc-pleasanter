# Behaviours that change designs

Each entry: what happens, why it matters, what to do. IDs refer to `docs/review-findings.md` in the framework repository.

| ID | Behaviour (version) | Consequence | Do this |
|---|---|---|---|
| D3 | SiteIds hard-coded in script strings are not remapped by site packages or the API (1.5.2) | A copied site's script silently reads another environment's data (seen in slice #1: stg read dev) | Use `${site:<name>}` in git; `pls pack` resolves per environment; lint L-REF-01 |
| D4 | `updatesite` replaces SiteSettings entirely (1.5.2) | Partial payloads delete settings; deploys overwrite customer UI edits | Complete payloads only (L-DEP-01); drift check before every deploy |
| D4a | `updatesite` has no conditional write: the API cannot say "only if unchanged since …" (design limit, not a probe result) | A UI edit saved between pls reading a site and writing it is overwritten without a trace | pls reads `UpdatedTime` in the preflight and again right before each site's write; release when nobody edits the sites (ADR-0014 TB-8) |
| D5 | Secrets in scripts are visible through `getsite` | Anyone with site-settings read access gets the key | No secret values in configuration; gateway pattern; L-SEC-01 |
| D7 | Shared server script with top-level `const`/`let` → every save fails `ServerScriptExecutionFailed` when combined with another script (1.5.2) | Whole site unusable for record saves | `var` in shared scripts; L-SCR-01 |
| D8 | Save-time normalisation: defaults added, default values dropped (1.5.2) | False drift if git is not canonical | `pls canon`; after first deploy, export → unpack; L-CAN-01 |
| D9 | Checkbox view filter is 2-state (only "checked") (1.5.2) | Cannot express "not yet done" with a checkbox in a display condition | Model states with **Status** or a choice column |
| D10 | API process execution enforces the display condition (1.5.2) | Display condition is a real guard, not just UI | Rely on it; test it with a negative API test |
| D11 | Removing a choice that records already use is data-impacting | Reverting a customer's added choice can orphan data | Resolve drift via `pls classify`; prefer accept + requirement |
| — | Adding a new status | Every view, notification condition and script that enumerates statuses must be checked (e.g. an "open items" view filtering on the old status list hides records in the new status) | Include a status-impact step in every design that adds a status |
| — | Server script time limit ~10 s | Slow external calls abort the save | Timeouts below 10 s; gateway with its own timeout |
| D12 | Removing a column / choice / status definition keeps stored values (1.5.2): column value hidden but kept, comes back when the slot is defined again; removed choice/status stays on the record and appears as an orphan option on the edit screen | "Removed" ≠ "deleted"; reusing a slot shows someone else's old data | Treat removals as data-impacting; never reuse a slot that held data; migrate values before removing a choice/status |
| D13 | `bulkupsert` with `Keys` = update matched records, create the rest (1.5.2) | One call per migration batch | Use for migrations; key on a business identifier column |
| D14 | API record updates did not create versions (`Ver` stayed 1) (1.5.2) | No undo from history after a data change | Back up affected records first (runner `backupRecords`) |
| D15 | `updatesite` accepts `InheritPermission` + `Permissions` (`Type,Id,Value`); keys omitted → permissions untouched (1.5.2) | Permissions can be deployed, but principal IDs differ per environment | `config/<site>/permissions.json` with `${principal:x}`; lint L-PERM-01 |
| D16 | Summary (集計, configured on the **child** site, e.g. `{Type: Total, SourceColumn: NumA, LinkColumn: ClassA, SiteId: parent, DestinationColumn: NumB}`): every child create/update/delete recomputes the **full** total for that parent (empty = 0). Adding/changing a Summary via `updatesite` does **not** recalculate existing parents; there is no API sync endpoint (`synchronizesummaries` → 400). Updating one child record (even with an unchanged value) recalculates its parent (1.5.2) | Past data shows 0 until a child changes | Classify Summary changes as data-impacting; migration = touch one child per parent after the release |
| D17 | `EditorReadOnly` is a screen setting only: the API can still write the column (1.5.2) | A "read-only" total can be overwritten by API clients or bulk imports | Do not rely on it for integrity; recompute (D16) after imports |
| D18 | `bulkupsert` updates only the columns given (others kept); if a key value matches **several** records the call returns HTTP 400 「条件に一致するレコードが複数存在します。」 with 0 added / 0 updated (1.5.2, PR-3) | A non-unique key stops the migration | Check key uniqueness in the backup before running; key on a unique business id |
| D19 | Site permission value **1 (Read)** for a group (1.5.2, PR-1/PR-2 with a test user): records can be read on the site and on child sites that inherit its permissions; attachments can be downloaded; `getsite` is readable; create / update / delete / process execution / comments → **HTTP 403** 「この操作を行うための権限がありません。」. The edit screen hides save/delete, **but still shows process buttons whose display condition matches** (e.g. エスカレーション) — pressing them is refused (403) (corrected after slice #2 T-015; the first probe had no matching process). A site without rights → 404 | Read-only role = value 1; note `getsite` exposes site settings (D5) | Use 1 for view-only roles; add Export (32) only if the role must export |
| D20 | Process access control is stored on the process as `Groups` / `Users` / `Depts` = lists of principal IDs (an `AccessControl` object is dropped; empty lists are dropped). With it, the process button is **not rendered** for users outside the lists, and API execution is refused (403 for a read-only user; HTTP 500 ApplicationError seen for a writer outside the list). A process **without** access control is rendered for every user who can open the record, including read-only users (D19) (1.5.2, PR-4) | Hide actions from roles that must not use them | `pls` maps these IDs to `${principal:x}` (L-PERM-01) |
| D21 | Executing a process through the API (`ProcessId`) when the process has **no display condition** (`View` absent) → HTTP 500 ApplicationError, nothing changed; the same process with `View.ColumnFilterHash` (e.g. `Status ["100"]`) works, and outside the condition → 400 (D10) (1.5.2, PRB-001 on an Issues probe site; `CurrentStatus` alone is not enough). The HTTP 500 noted in D20 may have the same cause — unconfirmed | A process without a display condition cannot be tested or used through the API. **A process with no `View` object at all also breaks the UI:** opening a record of the site fails with a server error (D21 probe site 44743, seen by Nam 2026-11-08; gone after removing that process). A process whose `View` holds only defaults (no filter) does not: adopted site 797 has 7 such processes and works. The UI always stores a `View` object, so only configuration written through the API can lack it. A `View` with only defaults (no filter) **runs through the API** (HTTP 200, status changed; probe D21-process-view-without-filter, 2026-11-08): the condition is then only `CurrentStatus`, and the button shows on every record in that status | Always give a process a display condition (at least the status it starts from) |
| D22 | A column that is **not in `EditorColumnHash`** is not usable: API `get` omits it, a Summary does not write it, a process data change to it fails (1.5.2, PRB-001) | Columns defined only in `Columns[]` silently do nothing | Put every used column in `EditorColumnHash.General` (and `GridColumns` when listed) |
| D23 | Summary with `SourceCondition` (child view Id) + `SetZeroWhenOutOfCondition: true`, `Type: Count`: counts only children inside the view; when a child leaves it (e.g. status 返却済) the parent is recomputed (→ 0). A parent never linked has the value **empty** (API `get` shows 0). Numeric view filter `["0"]` matches stored 0 only; `["\t"]` (未設定) matched both empty and 0, not 1 (1.5.2, PRB-001) | "Has no open child" must cover empty and 0 | Filter `["\t","0"]`; DefaultInput does not fill API-created records |
| D24 | Issues view `Overdue: true` (also accepted as API `View`): records not in a completed status whose 完了 (`CompletionTime`) is **before today**; due today is not overdue; completed records leave the list. `CompletionTime: "YYYY-MM-DD"` is stored as `T00:00:00` (1.5.2, PRB-001; completed status = 900) | Overdue lists need no date filter | Use `Overdue`; keep the completed status at 900 |
| D25 | Issues: API create accepts `CompletionTime` before `StartTime` (no built-in check). Server script `context.Error('…')` in `BeforeCreate`/`BeforeUpdate` rejects the save: API HTTP 500 with that message, record not created (1.5.2, PRB-001) | Date-order rules need a script (rung 3) | Script with `var`, message in Japanese |
| D26 | `createsite` with `SiteSettings {}` returns `{Id}`; the new site has only `Version`, `ReferenceType`, `NoDisplayIfReadOnly`, `NotInheritPermissionsWhenCreatingSite`, and inherits the parent's permissions (`InheritPermission` = parent) (1.5.2, ADR-0007 bootstrap) | Skeleton = defaults; built-in columns are implicit | Start `config/` from the skeleton export |
| D27 | `ValidateRequired` is a screen setting only: API `create` without the column succeeds (HTTP 200) (1.5.2, equipment demo T-102) | "Required" does not protect data written through the API or imports (like D17) | State required fields as screen behaviour in requirements; a script (rung 3) only if API writes must be refused |
| D29 | `Htmls`, `Scripts`, `Styles` round-trip through `updatesite` with 0 differences: Japanese text, CRLF, template literals, `<script>` inside an HTML block, `Disabled` kept. Items: `Id`, `Title`, `Body`, screen flags `All`/`New`/`Edit`/`Index`, `Disabled`; `Htmls` also `PositionType` (1000, 1010 seen). No `Name` (1.5.2, BR3 probe site 44734) | The custom layout of a screen can live in git and be deployed | `pls` unpacks them to `scripts/`, `styles/`, `htmls/` (`script-<Id>` when no Name); ids inside bodies → `${site:x}` (D3) |
| D30 | Dashboard parts (`DashboardParts`): `Type` 0 quick access, 1 timeline, 3 HTML, 4 calendar, 5 kanban. Types 1 and 4 **need `View`** (an object; `{}` is enough): without it `updatesite` fails with HTTP 500 and an HTML error page. On save Pleasanter adds defaults (`CalendarShowStatus`, `DisableAsynchronousLoading`, `KambanAggregationView`, `KambanShowStatus`, `TimeLineItemCount`, `SiteId`) and fills `View`. Round trip of types 1, 3, 4: 0 differences; site ids in `SiteId` (int) and in strings (`TimeLineSites`, `CalendarSites`, `CalendarSitesData`, `HtmlContent`) map to `${site:x}` (1.5.2, BR3 probe site 44735) | A hand-written part can break a deploy with an opaque 500 | Keep dashboards in their exported (canonical) form; always give types 1/4/5 a `View`; types 0 and 5 not yet verified (`pls_scope`) |
| D31 | Background (scheduled) server scripts are tenant settings (tenant management → サーバスクリプト: 実行ユーザ, 無効, 共有, schedules hourly/daily/weekly/monthly/once). No API reads or writes them: `/api/tenants/get`, `/api/tenants/1/get`, `/api/tenants/gettenant`, `/api/items/1/gettenant` → 404 (1.5.2, BR3 read-only probe; manual). Enabled by `BackgroundServerScript` in `Script.json`; per-environment control from 1.5.7.0 (`BackgroundService.json` / `Service.json`) | Jobs cannot be exported, diffed or deployed by `pls` | ADR-0012 option B: files in git, manual deploy, a person verifies; they run on every environment where enabled (ADR-0010 `jobs`) |
| D28 | User choice column: `Columns[ClassX].ChoicesText = "[[Users*]]"` is stored as given (`updatesite` → export round trip 0 differences, also with `ValidateRequired: true` on the same column). Through the API the record value is the **user id as a string** (`ClassHash.ClassB: "1"` written by `create` and read back unchanged by `get`) (1.5.2, MADLAB dev, equipment-loan demo R-20261105-01-dev, T-003/T-005/T-006/T-008). Not covered by this evidence: the screen dropdown contents (which users are listed), and whether a non-existent user id is refused | A "pick a person" column needs no script; tests and migrations write user ids, which are environment-specific | Use `[[Users*]]` for a user picker; pass the user id in tests as `--var` (never hard-code it in a spec); map ids per environment in migrations |
